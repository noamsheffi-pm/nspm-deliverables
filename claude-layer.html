Step 1

Fill CLAUDE.md before anything else

The install script put CLAUDE.md in your vault root. Claude reads it at the start of every session. It is the single biggest difference between output that sounds like you and output that sounds like a PM textbook. About 15 minutes, once.

Where they live

The script puts them in System/Agents/Claude/commands inside the vault, and links ~/.claude/commands to that folder. So you can read and edit a command in Obsidian and Claude picks up the change on the next run. If you already have a real ~/.claude/commands folder, the script leaves it alone and prints the command to link it yourself.

The commands

What each one actually does
Start here

/workplan

Creates or updates an initiative's 00-workplan.md. It is the only command that writes the frontmatter spine, so every other command and every dashboard view depends on what it produces.

It asks for three things: a short name, the area, and one line on the problem. Not the solution.

Run it a second time on the same initiative and it switches to update mode. It never overwrites the file. It changes only what moved, stamps last-reviewed, and appends one line to the session log.

Two rules it holds you to

next-action is one concrete sentence with an owner in it, not "follow up". And if it sets a blocker, it moves status to blocked in the same edit, so the two never drift apart.

Core artifact

/prd

Writes a PRD into the initiative folder and links it back to the workplan. It reads the workplan first, because the problem statement lives there, not in the PRD.

The rule that decides quality: the problem section must not contain the solution. If your input mixes them, it pushes back before writing. A PRD whose problem section already assumes the answer cannot be disagreed with usefully.

Every requirement needs an acceptance line someone could check. If it cannot write the acceptance, it says the requirement is not ready. Claims with no evidence are marked no evidence yet and left visible rather than smoothed over.

Week 2

/meeting-prep

One page before a meeting: what is still open from last time, where your initiatives in that area stand, three questions to ask, and what they will likely ask you.

Three questions maximum. A list of ten is a dump, not a prep. Every open item names the note and date it came from, so you can check it.

It works only from the vault. If there are no previous notes it says so and gives you the agenda section alone. That is why it gets useful in week 2 and not on day 1.

Closes the loop

/meeting-summary

Paste a transcript or your own rough notes. It pulls four things apart and keeps them separate: decisions, actions, open questions, and everything else. Most people write all four as one paragraph, and then nothing is findable later.

Every action needs an owner and a date. No owner means it is not an action, it is a wish, and it gets flagged as unassigned. If the room did not reach a conclusion, the note says unresolved. It will not smooth a disagreement into agreement.

Then it updates the initiative's workplan: decision rows, next-action, blocker, last-reviewed. It shows you those edits before making them.

This is the loop that keeps the vault alive

Meeting happens, summary writes the workplan, dashboard shows the change. Without this step the frontmatter goes stale in about two weeks and the views start lying to you.

How to use them

Four habits
Reject freely
Every command produces a draft, not a result. Deleting half of what it writes is normal use, not failure.
Edit the command itself
If it keeps getting something wrong, open the file in Obsidian and change the instruction. That is faster than correcting it every run.
Feed it real input
A rough paste of your own notes beats a clean summary you wrote by hand. The mess is the information.
Never let it send
Drafts get shown in the chat. Nothing goes to Slack, Jira or anyone else without you looking at it first.

Not yet

Agents come later, and the gate is not a date

Agents are jobs that run on a clock and leave you a short read in the morning. They work by reading frontmatter across many initiatives at once and reporting what changed.

Why they are not here

With two workplans an agent has nothing to correlate, so it produces confident nonsense. The gate is roughly ten live workplans whose next-action and last-reviewed you actually keep current.

That is a few weeks of habit, not a date on a calendar. Tell Noam when you get there.
