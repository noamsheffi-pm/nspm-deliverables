Reserved Fields — dataspace-aware table

Mockup only. Built from cx-web-workspace@dbd08c4db and internal-cx-web-workspace-design@c9346d52. Three proposals on top of what ships: skeleton loading on dataset change, a status column in Schema explorer that follows the storage engine, and add and edit a keypath inline.

The edit flow implements the three known defects as fixed: Cancel restores name and type (CX-57950), a no-op Save is not counted as a change (CX-57951), and a suggested type is adopted only when you have not set one yourself (CX-57952).

Add and edit

  • Add puts a new row at the top in edit mode. Type a keypath, pick a type, confirm with Enter or the tick.
  • The keypath box opens a list under it: the observed field on the left, the type it was seen as on the right. Arrow keys move, Enter picks, Esc closes.
  • Picking a suggestion fills the type only if you have not chosen a type yourself.
  • Esc or the cross cancels and restores the row exactly as it was, type included.
  • Remove marks the row Removed and keeps it, so Revert can bring it back. Nothing leaves until you Save.
  • A row you edit back to its original values is not counted as a change.

What changes with the dataspace

  • On this tab, nothing but the header. Reset index and the ingest counters appear for frequentsearch only. The table itself is the same everywhere, because a declaration does not depend on where the data is stored.
  • In Schema explorer, the status column follows the engine: Mapping status for frequentsearch, Column status for default and system. Values are explained below.
  • Switch dataspace on the explorer tab and watch message. The same field is a Union type in the archive and a Mapping exception in OpenSearch. The archive reads it slowly, OpenSearch rejects it.

Two tabs, two jobs

  • Reserved fields is configuration. It is static: a keypath and the type you declare for it. It is what you intend.
  • Schema explorer is observation. It is dynamic: what the data actually did, per dataset, over a time range. It is where status belongs, and where the problem is visible.
  • So Reserve this field lives in the explorer, next to the problem, and writes into the configuration tab. That is CX-56997 in one screen.
  • And there is no status column on the Reserved fields tab. It holds a keypath and a type, which is all a declaration is.

Reserve from the explorer

  • Click any row in Schema explorer to reserve that field. The row is the target; the Reserve button in the Reserved column does the same thing for anyone who scans by column.
  • It opens a drawer. It is a confirm step, not a one-click write.
  • It shows every type the keypath was observed as, with the share of events for each, and lets you set or override the declared type.
  • The drawer states the cost of the choice before you commit it. Declaring message as String says 13% of values will be read as null, because reserving forces a cast and Object cannot cast to String.
  • An already reserved row offers Change, which opens the same drawer to override the type.
  • Confirming writes an unsaved change into the Reserved fields tab. Nothing reaches the server until you Save there.

Status vocabulary — Schema explorer only

These values live on the Schema explorer tab. The Reserved fields tab has no status column: it is configuration, and a declaration is the same wherever the data is stored. One keypath can be healthy in one dataspace and broken in the other, because Frequent Search is OpenSearch and the rest is the S3 archive, so the column says what this engine did with it.

What $d is

$d is the DataPrime data root: the whole raw event stored as one object. Any field without its own column still lives inside it. Reading one field out of $d means reading the whole event and digging the field out, for every row. That is the cost CX-44928 is about.

Most of this column has no data source today. Verified 15-09 against the schema-store protos. The reserved record (SchemaTemplateField) holds a path and a type, nothing else. Observation holds type, cardinality, occurrences and values, and no column or mapping status. So only Union type and Type mismatch are derivable on the client right now. Materialized, Unmaterialized and both Pending states all need backend work that nobody has scoped.
Why the Reserved fields tab has no status column. Reserving a field is a declaration: a keypath and a type. It is the same statement whatever the engine does with it afterwards. What the data actually did is an observation over a time range, which is the explorer's job and the observations API's data. Putting it on the configuration page also makes a static page look live, and it cannot be, because a fresh reservation has nothing to report until the next compaction or index reset.
The asymmetry worth remembering. A union field is rejected outright by OpenSearch as a mapping exception, and read correctly but slowly by the archive. Same field, same data, two different failures. That is why one column name cannot serve both dataspaces.

Unmaterialized is the state Amnon wants to remove. A reserved field can still lose its column today when the budget runs out. His ask in the 14-09 meeting was that reserved fields go in first, before the popularity ranking. If that ships, this chip should never appear on a reserved field again, which makes it a good way to check whether the change worked.

Reserving still has no confirmation. After you reserve a field, nothing tells you it took effect until the next compaction or index reset changes what the explorer shows. Moving the status to the explorer makes that honest rather than solving it. Whether the user needs a clearer signal is an open question.
