Status vocabulary — Schema explorer only

These values live on the Schema explorer tab. The Reserved fields tab has no status column: it is configuration, and a declaration is the same wherever the data is stored. One keypath can be healthy in one dataspace and broken in the other, because Frequent Search is OpenSearch and the rest is the S3 archive, so the column says what this engine did with it.

What $d is

$d is the DataPrime data root: the whole raw event stored as one object. Any field without its own column still lives inside it. Reading one field out of $d means reading the whole event and digging the field out, for every row. That is the cost CX-44928 is about.

OpenSearch — frequentsearch (this vocabulary is the one that ships)

ValueWhat happenedDoes reserving fix itCan we show it today
Mapped OpenSearch holds a mapping for the field and indexes it normally. Already fixed.🟢 Ships today as Mapping status.
Partially mapped Indexed for part of the time range. Yes for the keypath you reserve.🟢 Ships today.
Unmapped No mapping exists for the keypath in the selected range. Yes. Reserving writes the field into the index mapping.🟢 Ships today.
Mapping exception Multiple applications sent the same field with different data types. Not on its own. Fix the declared type, or fix the data. 🟡 Ships as a count per keypath (Mapping Exceptions column), plus a dataset-level counter on the Reserved fields tab.
Most of the archive column has no data source today. Verified 15-09 against the schema-store protos. The reserved record (SchemaTemplateField) holds a path and a type, nothing else. Observation holds type, cardinality, occurrences and values, and no column or mapping status. So only Union type and Type mismatch are derivable on the client right now. Materialized and Unmaterialized need backend work that nobody has scoped.
Why the Reserved fields tab has no status column. Reserving a field is a declaration: a keypath and a type. It is the same statement whatever the engine does with it afterwards. What the data actually did is an observation over a time range, which is the explorer's job. It is also the reason a reserved field cannot be merged into the snapshot as it stands: the snapshot is dated, the declaration is not.
The asymmetry worth remembering. A union field is rejected outright by OpenSearch as a mapping exception, and read correctly but slowly by the archive. Same field, same data, two different failures. That is why one column name cannot serve both dataspaces.

Unmaterialized is the state Amnon wants to remove. A reserved field can still lose its column today when the column budget runs out. His ask on 14-09 was that reserved fields go in first, before the popularity ranking. If that ships, this chip should never appear on a reserved field again, which makes it a way to check whether the change worked.

Add and edit — the fixes in CX-57950 / CX-57951 / CX-57952

  • Add field puts a new row at the top in edit mode. Type a keypath, pick a type, confirm with Enter or the tick.
  • The keypath box opens a list under it: the observed field on the left, the type it was seen as on the right. Arrow keys move, Enter picks, Esc closes.
  • Picking a suggestion fills the type only if you have not chosen a type yourself (CX-57952).
  • Esc or the cross cancels and restores the row exactly as it was, type included (CX-57950).
  • A row you edit back to its original values is not counted as a change (CX-57951).
  • Remove marks the row and keeps it, so Revert can bring it back. Nothing leaves until you Save.
