What changed on 06-09

Not signed off yet

This page is built from the 06-09 session read through a fragmented auto-translation. Harel has not confirmed the write-up and nobody was named to write the RFC. Ilya was not in the room and this reverses his position. Treat every claim here as the shape the room converged on, not as a committed contract.

Two things the room said are deliberately out of this page. The room named a third target mode on a TCO rule, a pipeline that creates no loop; only the two dataset modes are shown here, so the page stays on the dataset question. The room also called the layer "traffic management"; the screen is labelled TCO because that is what the product calls it today.

One thing on the TCO screen does not come from 06-09 at all. A rule holds several destinations, each a dataspace and a dataset. That is the shape the TCO policy screen already ships, read off the design repo, and it is here so the dataset question is asked against the real screen. The 06-09 session discussed a single target. Each destination starts with the dataset type: it filters the dataset list to archive or forwarder datasets, and on a dynamic destination it is the type the rule creates the dataset with. What fan-out adds to this page is the cost line: every destination stores a full copy, so a rule with three destinations bills at about three times the matched volume out of one quota.

The room retired "dataset rules with matchers" and split it into two features with two APIs

The old model had one object: a rule with a matcher that both selected datasets and carried their configuration. Editing a rule reached every dataset it governed. That object is gone.

Dataset Definitions

The dataset name is the key. No matcher field at all.

  • Fields: description, ingestion mode, entityType, physical location, retention, partitioning, PBAC.
  • A duplicate name returns an error.
  • It is a list of configured datasets and nothing more.

Config Templates

A second, separate feature: name, matcher, default configuration.

  • Citadel checks definitions first and only falls through to templates on a miss.
  • A matching template creates the definition.
  • Editing a template never changes an existing dataset. It shapes the next one created.

Why weaker on purpose

Harel's reason for preferring it: a bug in a template cannot corrupt live customer data, and the risk drops by about a factor of ten. He compared it to a Notion page template.

Two APIs means two screens or tabs, not one merged list. Redlus argued for one list with exact matches on top; Harel refused, because the concepts and the permission level differ. Editing a template is a weaker role than creating a dataset.

The argument that did not win, kept on the record

Redlus: one expression rule spawning logs-1 to logs-50 lets one config change reach all fifty. Promote them to concrete datasets and a retention change becomes fifty edits. He compared it to a PBAC group override and said "dataset group" may be a clearer name than "dataset rule".

Bulk update per field is the answer the room gave, and it is weaker: a batch action, not a live binding. Case 2 on the Simulation tab shows why one edit can no longer reach many datasets.

Dataset type is a property of the dataset

Archive covers S3, GCS and COS: queryable, access policy applies. Forwarder covers MSK, Custom Kafka and IBM Event Streams: not queryable, no access policy, no retention tag, PBAC muted, and excluded from DLI query suggestions.

The enum sits on the dataset record, not only on the physical location, so consumers can filter on it. You pick the type first and the location dropdown then shows only the matching locations. Harel will not settle the name until Citadel says whether they already hold such a property.

The three declared properties, and why empty is not one of them

The 20-08 constraints concept put three properties on the create form and offered two paths for each: declare it now, or leave it empty and let the first write settle it. The second path is gone by agreement. Ingestion mode, entityType and partitioning are declared at creation and cannot be left empty, so a new definition starts with all three unset and the save is refused until each one is picked. The concept's fourth field, an optional bucket name, is out of this page: the platform names the bucket.

Ingestion mode decides who writes the dataset: streaming, written continuously as it arrives at the pipeline, or summary, written by a background query execution. It also decides the pillar in practice, because a summary lands as jsonData rather than as logs. It locks at creation, since the two write paths cannot be mixed on one dataset.

The drawer belongs to the dataset

Today, clicking a dataset opens the rule that created it, which lets an admin change other datasets by accident. The drawer must show that dataset's own config, its physical-location history, and which template it came from.

Deferred, named, not rejected

  • Per-parameter inheritance and pass-through to the default, ordered per parameter rather than per rule. Harel raised it from the compliance case, a two-year retention on everything European crossing three rules, and compared it to Elasticsearch index templates.
  • Rule-ordering risk. Reordering can silently redirect traffic to a different physical location with no signal. Not a first-stage blocker.

Two things differ, not one. The placeholder syntax, $d.field and $1 against {name}. And the keypath root, $d for data against $l for label, which resolve from different places. Free text against validated is a third difference and it decides whether the field can be checked before save.

What no syntax fixes: the preview can only look backwards. The name is built per event at write time, from the template plus the value on that event. So a list of the names a template will produce is not a prediction, it is a report of placeholder values already received. Until matching data has been sent there is nothing to show, no dataset exists, and the admin cannot see what the rule will do. This is why the room called a simulation tool the answer, and it is the part the UI has to make obvious rather than hide behind a preview that looks complete.

Immutability, stated for the first time on 06-09

On a dataset that already holds data, entityType cannot be changed and validation must refuse it. Retention and quota limit can change. That constrains re-ingestion: a re-import cannot repair a wrong entityType.

Partitioning behaves the same way: an admin sets it at creation and cannot change it afterwards. The platform may still change its own internal granularity later, daily to hourly, and 06-09 required that this never make the caller write the data twice. That is a Citadel decision, not an editable field.

Both locks bind at creation and apply to a forwarder as well as an archive. Retention, access and partitioning do not apply to a forwarder at all.
