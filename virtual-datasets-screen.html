Virtual Datasets

A virtual dataset is a name resolved at query time. It can resolve to a list of datasets, a name pattern, an entity type, or a full DataPrime query. A virtual dataset is a view: it reads like a dataset but has no write path. Its name must be unique across datasets and virtual datasets, so source <name> resolves to exactly one thing.

⚠
Names must be unique across datasets and virtual datasets. A virtual dataset cannot take a name a dataset already uses, so source <name> resolves to exactly one thing. Enforced when the name is entered. Pending confirmation with Harel and Redlus. Operational logs and log events are separate entity types. Routing writes logs, fan-out writes logEvents, and a virtual dataset can read across both.

One entity type per virtual dataset, the same as a real dataset carries one. Resolves by entity type rather than by name, and new datasets of that type are included automatically.
A full DataPrime query, up to joins and groupbys. The source may be a dataset, a pattern, or another virtual dataset.
Access
🔒
A virtual dataset never grants access. Who can read what stays driven by the PBAC of each dataset this resolves to, evaluated per caller at query time. There is no visibility setting here to get wrong.

Members the caller cannot read are translated as a false scope and return no rows. The caller sees one general notice, “you may not have access to all the data” — not an error, and deliberately not a per-member warning, which would name the withheld dataset and leak the definition.

Who may see and manage the definitions themselves is a general role permission, read and manage, set in Settings › Roles.
