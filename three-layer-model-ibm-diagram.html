Where does the data go, and what does each layer know?

Three layers, and each one knows only the layer below it. That is why a TCO policy can route data without naming a bucket or a topic: it names a dataset, and the dataset knows where its data is kept. The same three layers are the three screens an admin fills in, in order.

THE THREE LAYERS

Read it bottom up. Storage at the bottom, the data collections in the middle, routing on top.

HOW DATA REACHES A DATASET

The top row is what an admin configures, in order. Below it, what happens when data arrives: a policy routes to one dataset by name, or to many at once through a pattern, and each dataset is stored in one of the buckets or sent to one of the streams. Click any box to isolate what it touches.

THE THREE SCREENS, IN ORDER

SCREEN 1 · PHYSICAL LOCATION

Add the object storage bucket or the Event Streams topic. Retention tags are set here, per location, because each bucket keeps its own. Today there is one predefined Event Streams entry.

SCREEN 2 · DATASET RULES

Create a rule: which dataset names it matches, where the data is kept, its retention and its access policy. One rule can configure many datasets, and the list is ordered so the first match wins.

SCREEN 3 · TCO

Route data to a dataset. A dataset appears in the list once data has actually been routed to it, so a new environment starts with rules and an empty dataset list.

Concept for review, not shipped behaviour. There can be several buckets and several streams, and a rule points at one of them. Access policy on a rule is hidden when the target is a stream, because data sent to a stream cannot be queried. The default dataset stays on the existing screen in the first phase.
