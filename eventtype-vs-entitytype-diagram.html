eventType vs entityType — how the type is carried at ingest

New Relic: the producer writes the type into the record. eventType is required in the Event API body and reserved on the Log API, where it is dropped during ingest. The record is self-describing and the platform enforces the split at the endpoint.

Coralogix: the record never names its type. Two separate paths put it in a dataset. The platform path registers a new entityType in cx-catalog. The customer path is a DPXL expression in the Traffic Processor that routes or fans out into default/<dataset_name> while the entityType stays logs. The second path is the one customers actually use, and it creates containers, not types.

How New Relic correlates an event to a log — three layers, only the coarsest is automatic

Layer 1 · entity
automatic

Entity synthesis matches resource attributes against definition rules and binds the telemetry to an entity. entity.guid, entity.name and entity.type are reserved and system-owned; producer-supplied values cause undefined behavior.

Answers "same service". Never "same request".

Layer 2 · trace
logs only

The agent injects trace.id and span.id into every log. Custom events get nothing unless the producer fetches trace metadata and stamps them by hand, per call.

A log and a custom event meet here only when someone remembered.

Layer 3 · record
manual

NRQL subquery join: FROM Log JOIN (FROM Purchase SELECT sessionId, amount) ON sessionId. Equality only, no type coercion, cardinality capped 1:100, inner LIMIT default 10 and max 5,000.

An analyst tool for bounded lookups, not a correlation engine.

There is no automatic event-to-log correlation in New Relic. The entity is the only free link, so "custom event, no correlation" genuinely disconnects the data: no union reaches it, no trace panel shows it. We chose a more permissive model. A DPXL-routed log keeps entityType = logs, so it is still a log and the union reaches it. New Relic can never return the same record twice, and we can. The duplicate is the price of the permission.

New Relic — the record says what it is

Event API body, eventType required and producer-set:

[{ "eventType": "Purchase", "account": 3, "amount": 259.54 }]

Log API body, same field reserved. The docs state it plainly: if it is included, it will be dropped during ingest.

{ "logs": [{ "timestamp": 1550086450124, "message": "User 'xyz' logged in" }] }

You cannot smuggle an event into the log pipe. The split is enforced, not conventional.

Coralogix — two paths, and only one is governed

Platform path. Radiant matches cx.integration.source.type against a rule in code, cx-catalog holds the entityType, pillar and target dataset. New type, PR and approval, 44 live.

Customer path. A DPXL expression in the Traffic Processor routes or fans out matching records into default/<dataset_name>. No registration and no approval, bounded only by a soft limit of 15 user datasets on top of the predefined system ones, raisable per team. The entityType stays logs. The customer created a container, not a type.

No exceptions. aiEvaluations was briefly proposed to route on the OTel payload field event.name, which would have been the one place we resemble New Relic. CX AI was required to move to cx.integration.source.type, so every entityType now routes on integration metadata and nothing in the platform reads a type out of the payload.

Why this decides the correlation argument

Every user-created log dataset is the same entityType = logs. Nothing distinguishes them by kind, so a consumer asking "where are my related logs" can only answer with a list of containers. That is the union in the spans view, and it is the only answer the model permits.

Fan-out is a copy, so one record can sit in several of those containers. New Relic and Datadog both make that impossible by construction. Ours is a deliberate product capability, which means the duplicate is ours to solve.

Key-based correlation is the way out. Reserve and inject the keys, and the container stops being the answer.

Three initiatives are already building cross-container reads in parallel: multi-dataset sources, wildcard, and alias. All three make the union easier and none of them dedups a fan-out copy.
